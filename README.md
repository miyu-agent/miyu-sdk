# Miyu SDK

> <sub>This document was generated by Anthropic's Claude Fable 5.2.</sub>

The Miyu SDK is two small libraries for writing Miyu extensions: one for Python (`python/miyu_ext.py`) and one for Rust (`rust/`, package name `miyu-ext`). The two share the same concepts and names.

What an extension can do is set by the protocol (see `docs/en/reference/extensions.md` in the core repository), and the SDK adds no abilities of its own. It wraps the part that every extension would otherwise write again: the handshake, sending and receiving one message per line, answering concurrent calls by their ids, cancelling, config pushes, exiting when standard input ends, and the exit code 1 rule.

## Python

The Python SDK is a single file that uses only the standard library and needs Python 3.9 or later. Copy it into your package's `bin/` directory, next to your program:

```text
hello/
├── package.toml
└── bin/
    ├── miyu-hello        # your program, first line #!/usr/bin/env python3
    └── miyu_ext.py       # the copied SDK
```

```python
#!/usr/bin/env python3
import os, sys
sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))
from miyu_ext import Extension

ext = Extension("hello", "0.1.0")

@ext.tool("hello_greet", "Greet someone by name.",
          {"type": "object", "properties": {"name": {"type": "string"}}, "required": ["name"]},
          access="read", display_name={"en": "Greet", "zh": "打招呼"}, subject="name")
def greet(args, call):
    return f"{ext.config.get('hello.greeting', 'Hello')}, {args['name']}!"

if __name__ == "__main__":
    ext.run()
```

The full example is in the `python/examples/hello/` directory. How to write the manifest is described in `docs/en/dev/manifest.md` in the core repository.

The same file works on all three platforms. On Linux and macOS, the system starts the program directly from its `#!` line (the program needs execute permission). On Windows, the core reads the `#!` line to find the interpreter, and `python3` looks for `python` (this needs core 0.8.0 or later). Miyu does not ship Python, so state in your package's description that it needs Python 3.9 or later.

| Write | What it does |
|---|---|
| `@ext.tool(name, description, schema, access=…)` | Defines a tool. The function receives `(args, call)` and returns text, a `Reply` or a full answer. `call.cancelled` tells you whether the call has timed out or a person has interrupted it |
| `Reply(text, error, data, detail, sent, end_turn, state)` | A full answer. `data` goes only to scripts in which the AI calls the tool with `miyu call` (one line of JSON); `detail` goes only to the interfaces, which draw cards from it; `sent` holds the pictures the AI sends; `end_turn` ends this turn here; `state` is this package's state in this session (`{}` clears it, `None` counts as not set, and the core does not accept the state from a failed answer; the state is passed on as given) |
| `@ext.tool(…, paths=…, background_parameters=…, runs_commands=…)` | Three more spec settings: which parameters are paths (`[{"parameter": "file_path", "write": True}]`); parameters that are offered only when the session can run work in the background; and that the tool runs commands. For details, see "Tools that edit files or run commands" below |
| `@ext.tool(…, plugin=…, role=…, scope=…, result=…)` | More spec settings, which you leave out when you do not need them: a venue plugin (the tool is offered in group chats and private chats only where that plugin is turned on); a role (`read_file`); the sessions it is narrowed to within `venues` (`any`, `local`, `local_main`, `local_main_attended`, `spawn`); and the shape of `data` (one line of text). `access` can also be `install` |
| `Reply(…).changed(path)`, `.read(path, lines)`, `.trashed(path, trash)`, `.todos(todos, done)` | The `effects` in the answer: files that were changed, read or moved to the trash, and the to-do list that was put in place. `changed` can carry `before` and `after` (`content_hash(…)`), or `before_text` and `after_text`, so the core can check once more |
| `call.checked`, `call.channel`, `call.command_env()` | The real paths that the core's check allowed (only for tools that declare `paths`); the `miyu call` channel (only for tools that declare `runs_commands`), and an environment for child processes with that channel already set |
| `@ext.command(name)` | A slash command defined in the manifest's `[[slash]]`. The function returns the text shown to the person; while the function runs, `ext.language` is the language of the connection on which the command was typed |
| `@ext.method(name, timeout_ms=None, later=False)` | A method called by your page, a widget button, an interface or another package (by bus name or by package id). The function receives `(params, caller)`; raising `MethodError(code, message)` returns an error with a code (the code goes in the error's `data.code`, and `data.reason` holds the same code); `timeout_ms` is how long the core waits (1000 to 600000, 30 seconds by default); `later=True` means the method is not registered until you call `ext.enable_methods([...])` (for example, once a model has downloaded), and `ext.disable_methods([...])` unregisters it |
| `@ext.on(method)` | Other calls and pushes from the core: `user.append`, `search.query`, `widget.watch`…. Raising `MethodError(code, message)` returns an error with a code, and the core reads `data.reason` (`search.query` returns `limited` when it hits its limit) |
| `@ext.on_config`, `ext.config` | Config pushes; the config received in the handshake is in `ext.config` |
| `@ext.ready` | Runs once on its own thread after the handshake and registration are done |
| `ext.call(method, params)` | Calls a core method (`blob.put`, `model.call`…). When the call is refused, it raises `CoreError`, and `reason` holds the reason code |
| `ext.fatal(message)` | For problems that a restart cannot fix, such as bad settings or a port already in use: it writes to standard error and exits with code 1, and the core does not restart the extension again |

During the handshake, the SDK checks the protocol's major version. If the major version does not match, the SDK explains why under the exit code 1 rule and then exits. Declare capabilities in the manifest truthfully: calling a method whose capability is not declared returns `needs_approval`.

**Testing**: you do not need to start Miyu for tests, because `FakeCore` plays the core inside the process:

```python
from miyu_ext import FakeCore
core = FakeCore(ext, config={"hello.greeting": "Hi"})
assert core.call_tool("hello_greet", {"name": "Ann"})["blocks"][0]["text"] == "Hi, Ann!"
core.close()
```

The fake core checks the three spec settings the way the core does (a wrong setting returns `bad_tool`; a tool that runs commands returns `needs_approval` when `approved` does not contain `tools.commands`, and everything is approved by default), and refused calls are recorded in `core.refused`. Like the core, `call_tool` sends `checked` (the declared paths resolved to real locations against `core.cwd` and `core.home`) and `channel` (a fake one, `core.channel`; the fake core does not serve calls made through it), and it checks the `effects` in the answer the way the core does: accepted effects are recorded in `core.effects` (with paths as real locations), dropped ones in `core.dropped`, each one a `{"tool", "kind", "why"}`.

To run this repository's own tests: `python3 -m unittest discover -s python/tests`.

## Rust

The Rust SDK's package name is `miyu-ext`. It is synchronous and depends only on `serde_json`. Inside a handler, you call core methods and read config through `call.core()` (commands, methods and other handlers receive `&Core` directly), which corresponds to `ext.call` and `ext.config` in the Python SDK.

```rust
use miyu_ext::{Extension, Reply, Tool};
use serde_json::{Value, json};

let mut ext = Extension::new("hello", "0.1.0");
ext.tool(
    Tool::new("hello_greet", "Greet someone by name.")
        .schema(json!({"type": "object", "properties": {"name": {"type": "string"}}, "required": ["name"]}))
        .subject("name"),
    |args, call| {
        let config = call.core().config();
        let greeting = config.get("hello.greeting").and_then(Value::as_str).unwrap_or("Hello");
        Reply::text(format!("{greeting}, {}!", args["name"].as_str().unwrap_or("there")))
    },
);
ext.run();
```

The full example is `rust/examples/hello.rs` (build it with `cargo build --example hello`, then put the program in your package's `bin/` directory as `miyu-hello`, or `miyu-hello.exe` on Windows). `FakeCore::start(ext, config)` does the same job as the Python fake core; to run the tests, run `cargo test` in the `rust/` directory.

The names in the two SDKs map to each other as follows (the next section uses them):

| Python | Rust |
|---|---|
| `@ext.tool(…, paths=[…], background_parameters=[…], runs_commands=True)` | `Tool::paths(json!([…]))`, `.background_parameters(&[…])`, `.runs_commands(true)` |
| `Reply(effects=[…])` | `Reply::effects(vec![…])` |
| `@ext.tool(…, plugin=…, role=…, scope=…, result=…)` | `Tool::plugin(…)`, `.role(…)`, `.scope(…)`, `.result(…)` |
| `Reply(state=…)` | `Reply::state(json!(…))` |
| `raise MethodError(code, message)` inside `@ext.on(method)` | `ext.on_with(method, …)` returning `Err(MethodError::new(code, message))` (`ext.on` without errors works the same as before) |
| `.changed(path)`, `.changed(path, before=…, after=…, before_text=…, after_text=…)` | `.changed(path)`, `.changed_with(path, Change { before, after, before_text, after_text })` |
| `.read(path, lines=(1, 20))`, `.trashed(path, trash)`, `.todos(todos, done=None)` | `.read(path, Some([1, 20]))`, `.trashed(path, trash)`, `.todos(todos, None)` |
| `content_hash(data)` | `content_hash(&data)` |
| `call.persona` (this turn's persona id, `None` when there is no persona), `call.read_only` (`None` when the call carries no permission, which means unknown; treat that as the strictest case and do not treat it as writable) | `call.persona()`, `call.read_only()` (`Option<bool>`) |
| `call.pictures` (the folder for pictures, given only to local sessions, `None` otherwise), `call.permission` (the whole `{"level", "read_only"}`, `None` when absent) | `call.pictures()`, `call.permission_level()` (both `Option<&str>`) |
| `call.checked` (a list), `call.channel` (a dict or `None`) | `call.checked()` (`Vec<&str>`), `call.channel()` (`Option<Channel>`) |
| `call.command_env()`: the whole environment (a copy of `os.environ` plus the channel) | `call.command_env()`: only the entries to add, for `Command::envs` |
| `FakeCore(ext, approved=[…], cwd=…, home=…)`, `core.channel = …` | `FakeCore::start_approved(ext, config, &[…])`, `set_cwd`, `set_home`, `set_channel` |
| `core.refused`, `core.effects`, `core.dropped` | `core.refused()`, `core.effects()`, `core.dropped()`, `clear_effects()` |
| `@ext.method(name, timeout_ms=…, later=True)`, `raise MethodError(code, message)` | `ext.method_with(Method::new(name).timeout_ms(…).later(), …)`, `Err(MethodError::new(code, message))` (a bare name returning `Err(String)` works the same as before) |
| `ext.enable_methods([…])`, `ext.disable_methods([…])` | `core.enable_methods(&[…])`, `core.disable_methods(&[…])` |

## Tools that edit files or run commands

The protocol is described in the core repository's `docs/en/reference/extensions.md` (`provide`, and the effects and command sections under `tool.call`), and how to write such tools is described in the sections on tools that change files and tools that run commands in `docs/en/dev/extensions.md`.

**Tools that edit files** (editors, formatters, renaming tools and the like): if you want your tool to show diffs and added and removed line counts like the built-in `edit`, and you want the AI not to have to read a file again after you change a file it has read, you need to do the following three things.

1. Declare `paths` in the spec and set `access` to `write`: the core runs its permission check on them (writing outside the workspace asks the person first, and you receive no call before the person agrees).
2. Write only to the locations in `call.checked`: these are the real locations that passed the check, in the same order as the paths in the arguments. Do not write to the paths in the arguments yourself (a link on such a path may have been swapped after the check).
3. Report `changed(path)` in the answer: you only say which file changed, and the core reads the content itself (the content before the change is read before the call is sent, and the content after the change is read after you answer). In the following cases the core drops that one effect, and the result is still returned as usual: the content is the same before and after; the path is not in `checked`; the path was checked only for reading, but the effect reports a change or a deletion; the kind is unknown; the shape is wrong.

```python
@ext.tool("replace_text", "Replace one exact piece of text in a file.", SCHEMA, access="write",
          paths=[{"parameter": "file_path", "write": True}])
def replace(args, call):
    path = call.checked[0]
    ...  # edit path
    return Reply(text="Replaced.").changed(path)
```

The full examples are `python/examples/replace/` and `rust/examples/replace.rs`, and the repository's tests run them against the fake core.

**Tools that run commands** (tools that replace the built-in `shell` or run commands in a container): add the `tools.commands` capability to the manifest, and write `runs_commands=True` in the spec. When the session has tools that scripts can call, `call.channel` is this call's channel. Start commands with `call.command_env()` as their environment (it sets `MIYU_CALL_SOCK` and `MIYU_CALL_TOKEN`, and puts `bin` first on `PATH`), and `miyu call` inside those commands then calls tools as this session. If the command was started by your extension process (as a descendant process), wait for the command to finish before you answer, because the channel closes as soon as you answer.

```python
subprocess.run(command, shell=True, cwd=call.cwd, env=call.command_env())
```

```rust
std::process::Command::new("sh").args(["-c", command]).envs(call.command_env()).status()
```

## Versions

The current version is v0.1.0. Each new release gets a `vX.Y.Z` tag, and `__version__` in `python/miyu_ext.py` and the version in `rust/Cargo.toml` are updated with it; the tag is made only after both SDKs pass their tests on all three platforms (`.github/workflows/ci.yml`). In a Rust project, add the dependency by tag:

```toml
[dependencies]
miyu-ext = { git = "https://github.com/miyu-agent/miyu-sdk", tag = "v0.1.0" }
```
